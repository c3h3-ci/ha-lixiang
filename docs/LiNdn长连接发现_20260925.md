# 🎯 重大发现：新式车控走 LiNdn 长连接，不是 HTTP

> 2026-09-25 · 反编译 8.27.0 后确认

## 结论一句话

**充电控制 / 按时出发 等命令走的是 LiNdn 长连接（ss4 模式），
不是我们一直在用的 HTTP `cmd/send`。**

这解释了为什么所有 HTTP 尝试都返回 `2009`。

## 两条通道对比

| | 传统 `cmd/send`（HTTP）| LiNdn 长连接（ss4）|
|---|---|---|
| **传输** | HTTPS 请求-响应 | 私有长连接 |
| **token** | MESH + VAT | **JOB_PORT** |
| **签名** | x-chj（11 段）| ss4（rnd/exp/sign）|
| **已打通** | ✅ | ❌ |
| **覆盖命令** | 寻车/闪灯/鸣笛/空调/座椅/车窗/尾门/锁/哨兵/拍照 | **充电控制 / 按时出发 / 场景模式 / 冰箱预约 / 宠物模式 / 洗车模式** |

## 打通的难点

### 1. LiNdn 协议本身

- 协议名 `LiNdn`，从字符串看有 `connect`/`disconnect`/`init`/`setCloudConnectionExtra`
- 可能是 WebSocket 上层私有协议，或纯 TCP 自定义协议
- 需要找协议实现（可能在 **native so** 里）

### 2. JOB_PORT token

```
XVehicleIDAASManager.refreshVehicleTokenState(vin, callback)
  → 需要追到实际的 token 请求端点
  → 参考：我们的 VAT token 是 /login/subidaas/v2_vat
```

### 3. ss4 签名

```
createSs4SignParams(params) 的字段：
  "cmdData" / "expireAt" / "signParams.entries" / "TimeOut"
  + "rnd"（随机）/ "exp"（过期）
```

## 六、★ 协议栈完整破解（从 liblivenet.so 提取）

### 技术栈

```
Rust 实现的 NDN（Named Data Networking）协议栈：
  · mesh-nfd-2.8.82          ← NDN 转发器（NFD）
  · nfx-sdk-2.2.3            ← SDK 封装
  · p3-ndn-kite / p3-ndn-*   ← 传输
  · tokio + hyper(HTTP/2) + rustls(TLS)
  · LZ4 / Zstd 压缩
  · SOCKS5 代理支持（多网卡绑定）
```

so 文件：`lib/arm64-v8a/liblivenet.so`（9.4 MB，strip 过的 ARM64）

### 核心端点

```
POST /li-ndn-gfm/v2-0/forwarding-hint?device_type=&device_id=&target_type=&target_id=
POST /li-ndn-gfm/v1-0/forwarding-hint?vin=<VIN>
POST /li-ndn-gfm/gfm-server/v2-0/nfd-face
GET  /localhop/nfd/li/gfm_info
```

GFM = Gateway Forwarding Manager（转发提示服务器）

### 认证头（全部已知！）

```
X-CHJ-Timestamp
X-CHJ-Nonce
X-CHJ-KMS-VERIFY-TYPE       ← 我们已知："Veh"
X-CHJ-KMS-VERIFY-ID         ← 我们已知：VIN
X-CHJ-KMS-JWT               ★ JWT（来自 /bcs-kms-jwt/jwt/iot2/v1-0/）
X-CHJ-Env
Content-Type
```

**★ 这些头与我们已有的 x-chj 签名研究完全一致**，
说明 LiNdn 只是把 HTTP 请求换了个传输通道，认证体系不变。

### HTTP-over-NDN 的包结构

从错误字符串反推：
```
"Invalid authority part in http-over-ndn interest name"
"Invalid request header part in http-over-ndn data name"
"Invalid sha256 part in http-over-ndn data name"
"Invalid response header part in http-over-ndn data name"
"Invalid segment part in http-over-ndn data name"
"Invalid method part in http-over-ndn data name"
"Invalid scheme part in http-over-ndn data name"
"Invalid http-over-ndn data name, it must starts with /li"
```

**→ 包名格式（推断）**：
```
/li/<authority>/<request-header>/<sha256>/<response-header>/<segment>/<method>/<scheme>
```

即：**把 HTTP 请求的各个部分编码进 NDN 的命名空间**。

### 工作流程

```
① App 启动 → 初始化内嵌 NFD（Embedded NFD initializing...）
② 向 GFM 请求 forwarding hint（带 X-CHJ-KMS-JWT）
③ 用 FH 建立到云端的 face（长连接）
④ 把 HTTP 请求编码成 NDN Interest 包（HTTP-over-NDN）
⑤ 通过长连接发送，等待 Data 包响应
```

**这不是"补几个参数"，而是【从头实现一个协议栈】。**
