## 三、「按时出发」的两个命令（重要区分）

### A. `LXVehicleControlTypeAcAppointment` + `Fe()`
```javascript
sendVehicleJob(LXVehicleControlTypeAcAppointment, {cmdData: Fe()})
```
`Fe()` 返回 11 字段：
```javascript
{battWarmUp:false, flLevel:"1"-"7", frLevel:"1"-"7",
 rlLevel:"1"-"4", rrLevel:"1"-"4", startTime:"HH:MM",
 steerSet:"1"/"0", switchOn:true, temp:"26", vin, workingDay}
```
位置：@4534838（`appointmentAC` 页面）

### B. `LXVehicleControlTypeAppointmentAC` + `tt()`
```javascript
sendVehicleJob(LXVehicleControlTypeAppointmentAC, {
  cmdKey: 'MoveOffModify' 或 'MoveOffAdd',
  destParams: 'mob.metaJobService.MoveOffOnTimeData',
  data: tt(), timestamp: Date.now()
})
```
`tt()` 返回 16 字段（含 8 个座椅 + acSwitch + weekOfDayStates）：
```javascript
{id, subSwitch, startTime, isWorkDay, weekOfDayStates,
 acSwitch, temp, flLevel, frLevel, slLevel, smLevel, srLevel,
 tlLevel, tmLevel, trLevel, steerSet, battWarmUp}
```
位置：@4523002

### ★ 哪个对应状态信号？
```
状态信号: Vehicle.CarSettings.MoveOffOnTime.Xmode
实测内容: {mainSwitch, maxItemCount, moveOffDatas: {id: {
            acSwitch, subSwitch, startTime, temp, isWorkDay, weekOfDayStates,
            flLevel, frLevel, slLevel, smLevel, srLevel,
            tlLevel, tmLevel, trLevel, steerSet, battWarmUp}}}

→ 与 tt() 结构【完全一致】
→ 所以 B（AppointmentAC + tt()）才是车机设置里的「按时出发」
→ A（AcAppointment + Fe()）是 App 内的另一条路径（可能为临时预约）
```

## 四-补、★ 矛盾核实：「增程器启动」到底是什么

### teammate 的结论
```
"remote_engine_start 是 RN 键；HTTP 层实为 remoteVehAuth + cmdData:{}"
证据：VehicleControlModel.smali:359-371
       LXVehicleControlTypeRemoteStart → "remote_engine_start"
```

### 我的反驳（三条硬证据）

**① `remoteVehAuth` 已被证实是「虚拟钥匙授权」**
```
XHttpRemoteStartControl.smali 里的全部字符串：
  "remoteVehAuth"                        ← cmdKey
  "Vehicle.Cabin.RmtVirtualKeyAuthSts"   ← ★ 关联信号
  "remote Start:  "                      ← 调试日志

RmtVirtualKeyAuthSts = Remote Virtual Key Auth Status
                     = 远程虚拟钥匙授权状态

→ remoteVehAuth = 虚拟钥匙授权（App 首页的「授权驾驶」）
→ 与"增程器"无关
```

**② 旧版 JS bundle 里完全没有「增程器」**
```
搜索 unicode 转义：
  '增程器启动' (\u589e\u7a0b\u5668\u542f\u52a8): 0 次
  '增程器'     (\u589e\u7a0b\u5668): 0 次
  '启动增程器' (\u542f\u52a8\u589e\u7a0b\u5668): 0 次

含 Engine 的键: []（空）

→ 若该功能真的存在，JS 层应有文案
```

**③ smali 里也没有**
```
grep -rl "增程器" apk_decompile/ideal/smali_classes*/  → 无输出
```

### 可能的解释
```
① 截图里 OCR 的「增程器启动」可能是【OCR 误识】
   teammate 的 OCR 结果：'[2422] HEHN 增程器启动  按下'
   "HEHN" 是乱码 → 整个条目可能是误识

② 或者车控页的按钮是【服务端动态下发】的
   证据：存在 'vehicleEventTagUnityControlConfig' 事件标签
   → 按钮配置由服务端下发，本地 bundle 里没有文案

③ 或者该功能在新版 App（8.25.3）才加入
   但新版是 Hermes 字节码，未反编译
```

### 我的判断
```
❌ 不应把 remoteVehAuth 实现为「增程器启动」
✅ 我们当前的 button.授权驾驶 = remoteVehAuth 是【正确的】
⏳ 「增程器启动」的 HTTP cmdKey 【仍未确认】—— 需反编译新版或用 App 抓包
```

**教训**：teammate 的"推断"（RN 键→HTTP cmdKey）缺少直接证据链，
我差点据此实现错误的功能。**必须要求代码级证据，不接受推断。**

## 六、🔴 重大修正：充电控制命令实际全部失败

> 2026-09-25 深度验证后的诚实复盘（详见 `docs/充电命令实测修正_20260925.md`）

### 实测结果（同一时刻对照）

| 命令 | 结果 |
|---|---|
| `remoteVehSearch`（寻车，对照）| ✅ `pushState=5 rc=0 执行成功` |
| `remote_charge_control` + controlType=1（充电上限）| ❌ `pushState=7 rc=2009` |
| `remote_charge_control` + controlType=2（电池保温）| ❌ `pushState=7 rc=2009` |
| `remote_charge_control` + controlType=3（充电启停）| ❌ `pushState=7 rc=2009` |
| `LXVehicleControlTypeAppointmentAC`（按时出发）| ❌ `pushState=7 rc=2009` |

### 我之前的错误

```
❌ 我用 send_command_raw 验证，看到返回 requestId 就判定"成功"
✅ 正确做法：用 send_command（含 cmd-result 轮询）
   pushState=5 → 成功；pushState=7 → 失败

requestId 只是【受理凭证】，不代表执行成功。
```

### 因此而无效的改动

| 改动 | 实际效果 |
|---|---|
| VAT scope 加 `"ChargingControl"` | ❌ 无效（对照实验证明 scope 不影响）|
| `switch.预约充电` / `select.充电模式` / `time.充电时间` / `number.充电上限` | ⚠️ 命令全部失败 |
| `switch.电池保温` | ⚠️ 命令失败 |

**注**：这些实体仍可【读取】状态（sensor 层正常），只是【控制】无效。

### 尝试过的 7 种方案（全部失败）

| # | 方案 | 结果 |
|---|---|---|
| ① | `cmdKey=remote_charge_control` + cmdData | ❌ 2009 |
| ② | `cmdKey=LXVehicleControlTypeStartCharging` | ❌ 2009 |
| ③ | `cmdKey=MoveOffModify` | ❌ 2009 |
| ④ | `cmdKey=mob.metaJobService.MoveOffOnTimeData` | ❌ 2009 |
| ⑤ | `cmdKey=MoveOffOnTimeData` | ❌ 2009 |
| ⑥ | `cmdKey=MoveOffModify` + `{destParams, data, timestamp}` | ❌ 2009 |
| ⑦ | 加 14 种 VAT scope 候选 | ❌ 2009 |

### 根本原因（推断）

App 用【新式 job 通道】，需要 **JOB 类型的 token**：

```smali
// XAbsHttpControl.smali:1915
const-string p1, "JOB"
invoke-interface {v0, v1, p1, v2},
    Lcom/chehejia/lib/vehicle/demand/OtherCapable;->getIDAADSVehicleToken(VIN, "JOB", callback)
```

我们用的是 MESH + VAT token，可能不适用于该通道。

## 十、纠正：集成被禁用是【用户主动操作】

2026-09-25 排查"实体 0 启用 / 162 禁用"时，
我最初判断为"故障"，实际是**用户主动在 HA 里禁用了集成**。

**记录要点**：
- `config_entry.disabled_by = "user"` → 表示用户操作
- 三层级联禁用（config_entry → device → entity）
- 修复需清三层，只改 config_entry 无效

**教训**：`disabled_by="user"` 优先判断为【用户意图】，
不要急着当故障修复，应先询问。
